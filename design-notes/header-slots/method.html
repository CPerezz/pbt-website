Method and data.

Every note on the account header uses the data below. Every measured number in a note links to the raw query output behind it; hover a number to see its files.

  • Data. xatu's canonical execution tables in ethPandaOps' ClickHouse, queried through the panda CLI. A storage-read row is one (transaction, contract, slot) the transaction touched, written slots included, so one row is one cold charge. Those reads are complete only from block 24,700,000, so every read-based number covers blocks –: ranges of 1,000 blocks, one every 10,000 ( blocks, transactions).
  • Checks. In every range, every written slot appears among the touched slots ( missing), and every transaction has its touched-account rows ( missing). Some ranges hold exact duplicate rows, so every count reads its source through DISTINCT.
  • Writes are net per transaction, so a slot set and reset within one transaction is invisible: write savings are a lower bound. Access lists aren't in the data, so a few slots counted as cold were pre-warmed.
  • State is rebuilt by xatu's CBT tables at block 26,300,000, over all 256 address prefixes. Their total, 1.69 B live slots, matches our mainnet snapshot: accounts and buckets at block .
  • Paths and witness come from a model. A header path is about 2 + log₂(accounts) levels. A storage path is 1 + log₂(buckets) levels plus log₂ of the contract's groups. Paths opened in the same block share their top log₂(paths) levels. Bucket sizes come from CBT live-slot counts; ranges are shown with and without 64 header slots subtracted.
  • Gas rules are hypothetical. EIP-8297 changes no gas, and no PBT gas schedule exists yet.
  • Expectations in each note's first part are the hypotheses we started from, not measurements.

To rerun everything from scratch (about 30 minutes):

panda auth login
cd design-notes/header-slots/queries
python3 run.py        # every query through `panda clickhouse query-raw`, resumable → ../data/raw/*.jsonl
python3 analyze.py    # → ../data/summary.json
python3 labels.py && python3 analyze.py   # names from the contracts themselves (cast + public RPC)

The SQL is one file per question, linked from each note's data part. All of it is in queries/ on GitHub.
