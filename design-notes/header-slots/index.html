The first 64 slots.

EIP-8297 stores every account's storage slots 0–63 inside its header, next to its nonce, balance and code hash. Does that buy anything? We measured it on mainnet transactions (one 1,000-block range in every 10,000, over seven months): what it saves the tree today, what a gas rule that treats the header as one unit would save users, and whether 64 is the right number.

One stem per account

Each account has a header stem: 256 leaves under one key prefix, 0x00 ‖ key_hash(address). EIP-8297 puts the basic data (nonce, balance, code size) at position 0, the code hash at 1, a 7702 delegation at 2, and storage slots 0–63 at positions 64–127. Slots from 64 up live in the storage zone, in groups of 256 consecutive slot numbers under the contract's own bucket. Mapping entries hash to random slot numbers, so each one lands in its own group.

Five terms are enough for the rest:

  • Path: the branches from a leaf up to the state root, about 31 levels for a header ( accounts in our mainnet snapshot) and about 24 down to a bucket ( buckets), plus the levels inside the bucket. Leaves under one stem share everything above it.
  • Witness: what a stateless or zk verifier receives with a block: each value the block touched plus the sibling hashes along its path. Every separate path costs a few hundred bytes more.
  • Cold and warm (EIP-2929): the first touch of a slot in a transaction costs 2,100 gas, later touches 100. Changing a slot costs 2,900 more (20,000 if it was zero).
  • Group 0: slots 0–255 of a contract. EIP-8297 splits it: 0–63 in the header, 64–255 in the bucket.
  • The header is always open: to run a contract the node needs its code hash and code size, both in the header. So every SLOAD and SSTORE lands on an account whose header the block already opened. A slot in 0–63 adds one leaf to that open stem; any other slot needs a path of its own.

EIP-8297 does not change the gas schedule. Group A asks what a gas rule built on the last point would save; groups B to D look at the tree itself. Clients today still read each slot separately from their flat databases (geth and Besu key every slot by (account, slot), Nethermind keeps slots in their own column), so "free" here means free for the tree and the witness, not yet for the disk; see C3.

group A · a gas rule that treats the header as one unit

A1 · Free reads of slots 0–63

situation

Calling a contract opens its header, and most contracts then read their own low slots on every call: USDT reads its owner/paused word, fee settings and upgrade flag; Uniswap pools read their price and liquidity; Safes read threshold and nonce. Each first read in a transaction pays 2,100 gas.

why the header

Those slots are leaves of the stem the transaction already opened. The witness needs one more 32-byte leaf and a few hashes inside the stem, not a second path into the storage zone.

rule tested

Once the account is opened, the first touch of one of its slots 0–63 costs a warm read (100) instead of 2,100.

A2 · Cheap header writes after the first

situation

A Uniswap V3 swap changes the price word, fee growth and protocol fees; a V2 swap changes reserves and price accumulators; a Safe bumps its nonce; a mint changes total supply. Each first change of a slot pays 2,900 gas whether or not its stem is already being rewritten.

why the header

Once one header leaf changes, the node re-hashes that stem and its path to the root anyway. geth re-hashes the whole stem in one go (trie/pbt/node.go hashAt), so further header writes in the same block add no hashing at all.

rule tested

The first header change in a transaction pays as today, unless the nonce or balance already changed it; every further header-slot change pays a warm-write price (100). Writes that create a slot keep their state-growth price.

Header slots take of all slot changes. Of the transactions that change a contract's header slots, change two or more, but only also change that contract's nonce or balance. The rule discounts of header-slot changes and saves of gas ( at a warm-write price of 1,000).

Who gains

group B · what the tree saves today, without any gas change

B1 · "One path instead of two"

claim

A transaction that changes a contract's balance or nonce and one of its first 64 slots updates one path instead of two.

but

It needs the header to change in the same block. And a contract that writes slots on both sides of 64 without touching its header now needs two stems instead of one, because group 0 is split.

Per block, contracts get one path instead of two: Curve pools whose ETH balance moves, the EIP-7002 withdrawal-request contract collecting its fee, and every new contract whose constructor writes header slots. get two instead of one, mostly Uniswap V3 pools whose oracle write lands at slot 64 or above while their price word sits in the header. Net: paths out of rewritten per block (), about fewer hashes. True, and too small to argue for the design.

B2 · Contracts that live in their header

claim

A contract whose storage fits in slots 0–63 never gets a storage bucket: deploying it writes one stem, and its whole state is one stem to read, prove or store.

Of contracts holding storage, keep all of it in slots 0–63 ( have a bucket; our snapshot counted at block ). Most need very little: hold four header slots or fewer, exactly one. Header slots are of all live slots (). Among new contracts that write storage when deployed, write only header slots.

This does not make the state smaller: every branch has two children, so a tree has one branch fewer than it has leaves in any layout. Header slots move leaves to shorter, shared paths.

group C · design choices the data can settle

C1 · Why 64, and not 4

EIP-7864 recently cut its header to 4 slots (no rationale given) and EIP-8369's AA-VOPS profile talks of 2 to 4. Fewer header slots leave more hot slots outside the stem and split group 0 more often; more slots catch little extra. of reads below slot 256 hit slots 0–3, slots 0–15, slots 0–63.

Keep 64. It catches of the reads a 256-slot header would and of the paths; 4 slots catch of what 64 does and lose paths on writes.

C2 · Put the proxy slots in the header

situation

Upgradeable contracts keep their implementation address in a fixed, hashed slot (EIP-1967, or the older zos slots) and read it on every call. USDC and much of DeFi do. Hashed means storage zone: a separate path per proxy, and no benefit from A1.

proposal

Map these five slot numbers to unused header positions 3–63. Contracts can't tell; the mapping stays one-to-one.

The five slots take of all cold storage charges ( in the sample). Each block would skip storage paths, about of witness, and under A1 users would save another of gas.

C3 · One flat record per header

situation

Most reads are answered by the client's flat database, not the tree, and every client stores each slot as its own record. So a header-slot read is still its own disk lookup.

proposal

Store the header stem (basic data, code hash or delegation, slots 0–63) as one record, so the account read brings its hot slots with it.

Each block reads accounts and distinct header slots: of its storage reads would need no lookup of their own. The cost is that every account read carries its header slots: more on average ( of account reads carry any), about per block. This is what would make A1's "free" true for the disk too.

group D · context

D1 · Are low slots fading?

Newer patterns keep state away from slots 0–63: namespaced storage (ERC-7201, OpenZeppelin 5), proxies, singletons such as Uniswap V4, transient locks. New contracts show it: of storage-writing deployments before block 15 M wrote only header slots, since block 22 M. Traffic does not: slots 0–63 took of slot writes in blocks 4–11 M (2017–2020), since block 11 M and since block 24 M, and of cold charges in the sampled 2026 ranges (low · median · high). The old hot contracts carry the load.

D2 · EIP-7702 accounts

When a delegated account sends its own transaction its nonce changes, so under A2 its header is already open and every header-slot write it makes in that transaction is cheap. Of delegated accounts, those that wrote storage in two days of blocks made slot writes: in slots 0–63, and in a transaction that also changed their nonce. Each delegate is all or nothing: some keep everything in low slots, the namespaced ones nothing.

What the data supports

Keep 64 header slots (C1). Fewer lose most of the reads; more add little.

Drop "one path instead of two" as an argument (B1). The argument that holds is about reads: the header is always open, so its slots cost the witness almost nothing (A1, B2).

If PBT gets its own gas schedule, price slots 0–63 with the header. It would save of gas today. Most of that overlaps with multi-block warming, so the two should be designed together.

Proxy slots and a flat header record are worth writing up (C2, C3). Both are cheap to specify or build, and the data says they matter: of cold storage charges, of storage reads.

Method and caveats

  • Data. xatu's canonical execution tables in ethPandaOps' ClickHouse, through the panda CLI. A storage-read row is one (transaction, contract, slot) the transaction touched, written slots included, so one row is one cold charge. Those reads are complete only from block 24,700,000, so every read-based number covers blocks –: ranges of 1,000 blocks, one every 10,000 ( blocks, transactions).
  • Checks. In every range, every written slot appears among the touched slots ( missing) and every transaction has its touched-account rows ( missing). Some ranges hold exact duplicate rows, so every count reads its source through DISTINCT.
  • Writes are net per transaction: a slot set and reset inside one transaction (a reentrancy lock) is invisible, so A2 is a lower bound. Access lists aren't in the data, so A1 counts a few slots as cold that were pre-warmed.
  • State (B2) is rebuilt from history by xatu's CBT tables at block 26,300,000; their total, 1.69 B live slots, matches our mainnet snapshot. Snapshot counts: accounts, buckets at block .
  • Paths and witness are a model: a header path is about 2 + log₂(accounts) levels, a bucket path 1 + log₂(buckets) plus log₂ of the contract's groups, and paths in one block share their top log₂(paths) levels. Bucket sizes come from CBT live-slot counts (range: with or without 64 header slots subtracted).
  • Long trends (D1) use writes only: 200 blocks every 250,000 from block 1,000,000. C3 uses 4 of 256 address prefixes over two days, which under-represents vanity addresses.
  • Gas rules are hypothetical. EIP-8297 changes no gas, and no PBT gas schedule exists yet.
