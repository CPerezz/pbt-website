Slots 0–63 belong in the header.

TL;DR Running a contract always opens its header, so storage slots kept there ride along. of cold storage charges hit slots 0–63, each block skips storage paths, and of contracts with storage never need a storage bucket.

Aclaim & expectation

EIP-8297 keeps every account's storage slots 0–63 in its header stem, next to its basic data and code hash. Running a contract always reads its code hash and code size, so the header stem is already open by the time the contract touches its storage.

The claim: slots kept there come almost for free. Reading one adds a leaf to a stem the block already opened, instead of a separate path into the storage zone. And a contract whose storage fits in slots 0–63 never needs a storage bucket at all.

We expected it to hold for two reasons. Older contracts keep their hot flags, counters and prices in their first slots: USDT's pause flag and fee settings, a Uniswap pool's price word, a Safe's threshold and nonce. And most contracts are small: clones, simple vaults, per-user contracts from factories.

Cconclusion

Justified. Slots 0–63 carry of cold storage charges and spare each block storage paths, and three in four contracts with storage live entirely in their header. The layout doesn't make the state smaller, since a binary tree always has one branch fewer than it has leaves. It gives the hottest slots paths that their header already pays for.

New contracts lean less on low slots, but traffic still does, because old hot contracts carry it. Two things stand between this and the full benefit: gas still charges a header slot like any other slot, and clients still read it from disk on its own. The proposals Charge slots 0–63 with the header and Store the header as one record take those on.
