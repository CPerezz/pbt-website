Charge slots 0–63 with the header.

TL;DR A header-slot read at the warm price once the account is open, and cheap header writes after the first: mainnet would use less gas, room for more transactions per block. But of the read saving overlaps EIP-8289's multi-block warming; shipped after it, the read half adds only .

Aproposal & expectation

EIP-8297 does not change gas, so a header slot is charged like any other slot: 2,100 for its first touch in a transaction, and 2,900 more to change it. The proposal is two rules that charge slots 0–63 with the header they live in:

  • Reads. Once a transaction has opened an account to run its code, the first touch of any of its slots 0–63 costs a warm read (100). The node pays almost nothing for it: the slot is one more leaf of a stem the block already opened (see the claim).
  • Writes. Once one header leaf changes, the node re-hashes that stem and its path to the root anyway, and further changes in the same block add no path hashing; a client may even re-hash the whole stem at once. So the first header change in a transaction pays as today, unless the nonce or balance already changed the header, and every further change to a slot in 0–63 pays a warm-write price (100). Creating a slot (zero to non-zero) keeps its state-growth price.

We expected the read rule to carry most of it: a transaction reads far more slots than it changes, and the write rule only discounts the changes after the first.

Cconclusion

Supported, designed together with EIP-8289. The rule is worth of gas today, spread over of transactions, and it barely depends on the exact prices: across the grid the saving moves by less than a point. The read half carries almost all of it, and most of the read half goes away if multi-block warming ships first. The write half is small but cheap to specify alongside.

For the disk to be as cheap as the gas, clients need the one-record header.
